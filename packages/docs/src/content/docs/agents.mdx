Codesm delegates bounded tasks to specialist roles. Each role has a defined tool
set, and role profiles can add instructions, select models, and restrict tools.

## Built-in specialists

| Role | Purpose | Capability |
|------|---------|------------|
| `coder` | Implement a focused change | Can edit, subject to parent permissions |
| `planner` | Prepare implementation steps | Read-only |
| `oracle` | Analyze difficult bugs and design decisions | Read-only |
| `librarian` | Research code across repositories | Read-only |
| `finder` | Locate relevant code | Read-only |
| `researcher` | Investigate a codebase | Read-only |
| `reviewer` | Review code and report issues | Read-only |

## Using specialists in the terminal

Ask for a specialist as part of your task:

```txt frame="none"
Ask the planner to inspect this change and propose implementation steps.
```

The main agent can call `task`, `parallel_tasks`, or `pipeline` to delegate work.
Specialist activity appears in the transcript with its role, model, status, and
result. Press **Ctrl+T** to inspect the full details.

The terminal's **Tab** key selects Smart/Rush model modes while idle and queues
messages during active work. It does not switch between Build/Plan agents, and
there is no `/agent plan` command. Use `read_only: true` in project configuration
to restrict the whole task to read-only tools.

## Role profiles

Configure existing roles in `codesm.json`:

```json title="codesm.json"
{
  "agents": {
    "reviewer": {
      "model": "openai/gpt-5.6-sol",
      "prompt": "Focus on correctness and security. Cite files and lines.",
      "tools": { "websearch": false },
      "max_iterations": 20
    },
    "coder": {
      "prompt": "Follow the existing documentation style when editing docs.",
      "tools": { "bash": false },
      "permissions": { "edit": "ask" }
    }
  }
}
```

Profiles tune built-in roles; adding an arbitrary profile name does not register
a new specialist. Use `main` to configure the main agent.

| Property | Purpose |
|----------|---------|
| `model` | Exact `provider/model-id` for this role |
| `prompt` | Additional instructions appended to the role prompt |
| `tools` | Map of tool names to booleans; `false` removes a tool |
| `permissions` | Additional permission restrictions |
| `reasoning_effort` | Reasoning setting sent to the provider |
| `max_iterations` | Maximum agent-loop iterations |
| `max_output_tokens` | Maximum output tokens per request |
| `context_tokens` | Context allowance for the role |

Role profiles cannot restore tools denied by the parent or a role's read-only
capability. See [Config](/config) for supported settings and precedence.

## Agent selection

The `delegation` setting controls how the main agent uses specialists:

```json title="codesm.json"
{
  "delegation": "adaptive"
}
```

Use `single` for the main agent alone, `specialists` to require explicit role
selection when delegating, or `adaptive` to allow automatic routing. Role profiles
and `routing_models` control model selection. `pin_model: true` keeps specialists
on the parent model.

## Shared execution and visible results

All specialist roles run through the same execution loop as the main agent.
Planner, Oracle, librarian, finder, researcher, and reviewer are read-only; coder
can edit. Workers inherit project rules, task constraints, the parent approval
session, tool restrictions, and the shared usage allowance. These capability
restrictions are enforced by the tool registry; project prose remains model
instructions, not an operating-system sandbox.

Independent reads may overlap. Mutations in one tool batch preserve their order,
and coder workers share one writer lock per checkout. Concurrent writers would
require isolated worktrees; the current runtime deliberately serializes them.
Workers cannot recursively invoke the task/orchestration tools.

The terminal shows a worker's role, selected model, waiting/running state, tool
evidence, final result, and estimated cost when rates are known. Press **Ctrl+T** or expand a finished
worker to inspect its evidence. Failed, stopped, cancelled, and interrupted runs
remain labeled as such. Saved sessions retain worker results and usage.

Escape cancels the active task and its workers. Shell timeouts and cancellation
terminate the shell's process group, including descendants. On resume, completed
tool exchanges remain in history. An interrupted call without a saved result is
marked as having an unknown outcome, so the agent must inspect current state before
retrying a possible mutation.
